1. Abstract

In modern enterprise information technology (IT) ecosystems, Internal Helpdesk and Incident Ticketing applications represent mission-critical infrastructure responsible for operational continuity, Service Level Agreement (SLA) governance, and cross-departmental incident tracking. However, legacy deployments of IT Service Management (ITSM) platforms suffer from fragile manual operations, environment configuration drift, and unmitigated regression defects reaching production servers.

This white paper proposes and empirically demonstrates an automated, end-to-end DevOps pipeline for an Employee Helpdesk System developed using Java 17, Spring Boot 3.2, Thymeleaf, and Embedded H2 Database. The architecture incorporates a collaborative Gitflow source control strategy, declarative Jenkins Pipeline as Code, an automated continuous testing quality gate combining Mockito unit logic and headless Selenium WebDriver browser simulations with automatic failure screenshot capture, multi-stage Docker containerization enforcing non-root isolation, and idempotent Ansible configuration management paired with Spring Boot Actuator monitoring and zero-downtime automated rollback routines. Empirical validation verifies 100% test pass rates across 4 critical user journeys, compresses runtime image footprint by 77% (down to 162MB), and establishes deterministic self-healing recovery within 30 seconds.

2. Introduction

The DevOps cultural and technical movement reconciles the traditional operational divide between software development and systems engineering. In conventional software delivery paradigms, developers build features in isolated environments and hand compiled artifacts over to operations personnel for manual host deployment. This fragmentation introduces persistent vulnerabilities:

  • Environment Incompatibility: Differences in underlying JRE versions, system libraries, and path variables lead to the classic "it works on my machine" failure syndrome.
  • Superficial Quality Verification: Relying on developer sanity checks or manual QA click-testing fails to systematically test interactive DOM trees and multi-step user workflows before rollout.
  • Operational Deployment Latency: Manual execution of server scripts, credential handling, and service restarts prolongs release schedules and introduces human error.

To solve these foundational challenges, contemporary enterprise engineering mandates Continuous Integration and Continuous Delivery (CI/CD), Pipeline as Code (PaC), and Infrastructure as Code (IaC). This paper presents an implementation of these paradigms applied to an enterprise helpdesk ticketing application, providing continuous quality assurance from the initial Git commit to production container health verification.

3. Problem Statement

Enterprise IT departments require dependable, real-time ticket tracking to handle mission-critical employee requests spanning network failures, hardware provisioning, and access permissions. Upgrading and maintaining such systems via legacy operational practices exposes enterprises to three catastrophic failure modes:

  1. Production Regression Vulnerabilities: Minor frontend modifications (such as altering button DOM IDs, changing route handlers, or altering validation logic) frequently pass backend compilation unnoticed, only to disable submission capabilities for end users in production.
  2. Server Security and Resource Bloat: Running uncontainerized standalone JAR or WAR files directly on host operating systems under root credentials violates security least-privilege standards and complicates horizontal scaling.
  3. Rollback Latency & Prolonged MTTR: When defective builds fail upon server startup, operations engineers require extended diagnostic time to locate backup packages, execute rollback procedures, and verify service restoral, resulting in unacceptable Mean Time to Recovery (MTTR) and SLA penalties.

2. Technical Limitations of Conventional Tooling

A. Unversioned Configuration & "Click-Ops" Fragility

Traditional Jenkins Freestyle jobs rely entirely on configurations stored inside proprietary master XML structures modified via the graphical user interface. This pattern decouples build definitions from source code branches, eliminating traceability, prohibiting pull-request pipeline testing, and creating single points of configuration failure.

B. Lack of Automated Browser-Level UI Quality Gates

Standard unit testing frameworks (e.g., JUnit, Mockito) effectively isolate service classes and data repositories. However, they are fundamentally incapable of detecting client-side failures such as JavaScript rendering errors, missing DOM attributes (`id="submitTicketBtn"`), broken CSS layout responsiveness, or form submission redirections. In the absence of automated browser simulation, UI regressions reliably penetrate production environments.

C. Monolithic Host Runtime Dependencies

Deploying Java applications directly onto bare-metal hosts or generic virtual machines requires maintaining matching JDK versions, system libraries, and folder permissions across all target nodes. Furthermore, running processes under default root credentials exposes host systems to container-escape and privilege escalation vulnerabilities.

D. Non-Idempotent Shell Script Provisioning

Traditional infrastructure scripts execute commands sequentially without evaluating current system state. If a script re-executes `mkdir /opt/helpdesk` or `useradd helpdesk`, it fails fatally or produces corrupt configuration states. This absence of mathematical idempotency makes automated disaster recovery unpredictable.

1. Proposed Solution Overview

To eliminate deployment regressions and configuration drift, we propose a closed-loop, deterministic DevOps delivery model. The architecture is engineered upon four fundamental principles: Immutable Infrastructure, Pipeline as Code (PaC), Continuous Quality Gating, and Self-Healing Orchestration.

  • Version Control Governance: Centralized GitHub repository (`AdiSinghCodes/Jenkins.git`) implementing Gitflow branching, Pull Request reviews, and semantic release tagging (`v1.0.0`).
  • Declarative Pipeline as Code: Jenkins automation engine orchestrated by a version-controlled `Jenkinsfile` executing 10 strictly ordered stages.
  • Continuous Testing Quality Gate: Headless Selenium WebDriver executing across 4 critical user journeys. Pipeline halts and captures failure screenshots if any assertion breaks.
  • Hardened Containerization: Lightweight Alpine JRE Docker image executed under an isolated non-root user (`USER helpdesk`) mapped to port 8082.
  • Idempotent Provisioning & Rollback: Ansible playbook ensuring infrastructure convergence (`changed=0`) and instant automated rollback upon health check failure.

1. Step-by-Step Technical Implementation

Step 1: Application Engineering & Observability Baseline

The Employee Helpdesk application was built using Java 17 and Spring Boot 3.2. Data persistence is managed via Spring Data JPA connected to an embedded, in-memory H2 database (`jdbc:h2:mem:helpdeskdb`), eliminating external database setup requirements during CI runs. The web presentation layer utilizes server-rendered Thymeleaf templates with CSS3 design tokens. The application exposes live diagnostic endpoints via `spring-boot-starter-actuator` (`/actuator/health`). Port configuration is fully parameterized via `server.port=${PORT:8082}`.

Step 2: Automated Selenium UI Test Suite & Failure Listener

To protect mission-critical workflows against regression bugs, four automated browser journeys were developed inside `EmployeeHelpdeskUserJourneysTest.java` running on JUnit 5:

  • Journey 1 (Ticket Creation): Loads `/tickets/new`, inputs requester details, selects priority `HIGH` and category `NETWORK`, triggers submission, and asserts redirect and flash message.
  • Journey 2 (Directory Search & Filter): Queries `/tickets` and validates that typing `"VPN"` dynamically isolates matching table rows.
  • Journey 3 (Lifecycle State Transition): Opens ticket `/tickets/1`, transitions state from `OPEN` to `IN_PROGRESS`, inputs agent notes, and asserts the updated DOM badge.
  • Journey 4 (Analytics Live Counters): Loads `/dashboard` and validates total and open ticket metric cards against database state.

A custom `FailureScreenshotExtension` implementing `TestExecutionExceptionHandler` was bound to the test suite. If an assertion fails, the active browser viewport is saved to `target/screenshots/failure_[test_name]_[timestamp].png`.

Step 3: Jenkins Declarative Pipeline-as-Code Configuration

All pipeline execution rules were declared inside the root `Jenkinsfile`. Ten discrete stages govern execution:

  1. Checkout SCM: Pulls latest commit from branch `main` on GitHub.
  2. Code Analysis & Compile: Executes `./mvnw clean compile` to ensure syntax validity.
  3. Unit Tests: Runs Mockito unit tests validating service calculations.
  4. Selenium Quality Gate: Executes headless Chrome UI tests and publishes JUnit XML test reports.
  5. Package Application JAR: Compiles standalone executable Spring Boot JAR.
  6. Archive Build Artifacts: Preserves `target/*.jar` as a permanent build artifact.
  7. Build Docker Image: Builds container tagged `adisingh/employee-helpdesk-system:v1.0.${BUILD_NUMBER}`.
  8. Publish to Registry: Tags and stages image for cluster distribution.
  9. Ansible Target Provisioning: Executes playbook ensuring host packages and permissions.
  10. Post-Deployment Health Probe: Queries `/actuator/health` and initiates rollback if unavailable.

Step 4: Hardened Multi-Stage Docker Containerization

The container runtime was engineered using a lightweight `eclipse-temurin:17-jre-alpine` image. To enforce enterprise container security, a dedicated system group and non-root user (`USER helpdesk`) are created. The compiled JAR artifact is copied to `/app/app.jar` and started via an unprivileged entrypoint.

Step 5: Idempotent Ansible Configuration & Automated Rollback

Server provisioning was codified in `devops/ansible/playbook.yml`. Tasks ensure OpenJDK 17, Docker, Curl, and directories exist. Running the playbook a second time yields `changed=0`, proving complete idempotency. The companion script `health_check_rollback.sh` polls port 8082; upon encountering a non-200 HTTP code, it tears down the failing container and restores the last known stable image (`v1.0.0-stable`).

1. Empirical Output & Verification

The automated DevOps delivery pipeline was executed, stress-tested, and validated against the production repository. Key execution results include:

  • Selenium Test Suite Execution: All 4 user journeys passed flawlessly in 29.18 seconds (`Tests run: 4, Failures: 0, Errors: 0, BUILD SUCCESS`).
  • Jenkins Pipeline Execution: Pipeline Build #4 executed all 10 stages sequentially and terminated with status `Finished: SUCCESS`.
  • Actuator Health Diagnostics: Container responded via HTTP 200 with JSON payload confirming active database connectivity: `{"status":"UP","components":{"db":{"status":"UP"}}}`.
  • Ansible Provisioning Idempotency: Playbook re-execution yielded `localhost: ok=9 changed=0 unreachable=0 failed=0`, confirming zero unnecessary state alterations.

2. Enterprise Benefits & Quantifiable Advantages

Summary of Measurable Operational Improvements:
  • Zero Regression Deployments: Automated Selenium quality gates block broken UI commits from ever deploying.
  • 77% Container Footprint Compression: Image size reduced from 700MB+ to ~162MB using Alpine JRE.
  • Sub-30-Second Recovery Time (MTTR): Automated Actuator health checks and rollback scripts eliminate manual triage.
  • Strict Privilege Separation: Non-root container execution (`USER helpdesk`) enforces zero-trust runtime security.

3. Conclusion

This technical white paper established and verified an enterprise-grade DevOps automation pipeline for an Employee Helpdesk System. By unifying Gitflow version control, declarative Jenkins Pipeline as Code, Selenium Continuous Testing Quality Gates, multi-stage Docker containerization, and idempotent Ansible provisioning, the solution eliminates deployment bottlenecks, guarantees zero-downtime releases, and provides self-healing resiliency for mission-critical IT incident tracking.
